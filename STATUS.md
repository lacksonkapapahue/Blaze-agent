## blaze-docs (v0.28.4, versionCode 100)
- **Branch:** `blaze-docs` (off main at 40393aa, v0.28.1; main merged in at 86a0429, v0.28.3). Built-in docs about Blaze as an on-demand lookup: generated at build time (`BlazeDocsTask`, `app/build.gradle.kts`; hand-written `app/blaze-docs/about.md`), indexed into blaze.db on the first launch after an update (`blaze_docs` + FTS5 `blaze_docs_fts`, meta `blaze_docs:sig`), reached only via `blaze_docs_search` / `blaze_docs_read` (`agent/BlazeDocs.kt`). Prompt: one static line + the repo URL. GitHub near-miss URLs fixed (`ToolLeak.fixBlazeUrl`). Work card total = the turn's real run time, frozen at finish (`ui/WorkTime.kt`, `ChatMessage.startAt`). See CHANGELOG v0.28.4.
- **Audit findings (v0.28.4):**
  - Memories live in blaze.db as rows of the shared `memories` table (schema v1, `store/BlazeDb.kt` MIGRATIONS) with FTS5 `memories_fts`; subjects / related in the side table `mind_mem`; the journal in `mind_journal` + FTS5 `mind_journal_fts` (`agent/MindStore.kt`, `EXTRA`). `Mind.init` opens `filesDir/blaze.db` (`agent/Mind.kt`). Nothing writes memories to a .md file.
  - `agent/Memory.kt`'s prefs list `memory` is not dead but is not a store either: `reload()` mirrors the table into it (write-only backup for downgrade / backup export), `legacy()` is read once for the import (`mig_memory`) and after a backup restore (`mergeLegacy`), and the old list is used only when no memory store could open (`Mind.db() == null`). It never reaches the prompt while the store is up (`Memory.promptBlock` returns `Mind.promptBlock()` when `Mind.ready`).
  - The prompt's memory part is `Mind.block`: MIND_RULE + pinned core (profile + preference lines, ≤ `CORE_MAX` 1,600 chars) + subject index (≤ 14 subjects per kind, "+N more"). Measured by `PromptBudgetTest`: 500 memories + every doc indexed grow it by < 1,500 tokens (budget 6k) with no docs text and only pinned-core memories in it. `Learning.review` and `MindReview` send only related lines / the core, never the whole list.
  - Skills: SKILL.md files on disk (shared format). Per turn `SkillMatch.forTurn` injects at most 3 matched skills within 6,000 chars (`SkillMatch.block`, Agent per-turn block) plus `SkillMatch.lookupBlock` (≤ 3 short descriptions). Nothing reads all skills into the prompt; `SkillMatch.cached()` reads every SKILL.md from disk at most every 20 s for matching only. Core skills' pinned rules: ≤ 6,400 chars, static.
  - Large text every turn (static, so it stays in the provider's cached prefix): the systemPrompt literals (~8.8k chars, ~3.5k of them the phone-control block), core skills (~5.6k chars), `RichReplies.PROMPT` (~4.8k chars, off with Visual answers), `ViewRouter.PROMPT`, `AnswerStyle.RULE` (~0.9k). Per-turn when matched: up to 6k chars of skills. Fixed here: a question about Blaze itself no longer pulls in skill packs or a specialist (Luke's question had attached five coding skills, ~6k chars, and the Coder). Not changed: the project brief is pinned whole every turn (user-written, unbounded; consider a cap); the tool schemas (core + matched groups) are the other big per-turn input.
